## 1. 文档目的

本文档面向开发、维护、测试和交付人员，说明当前工程的软件架构、核心模块职责、初始化流程、数据流、配置模型、存储设计、OTA 方案以及当前实现边界。

## 2. 设计目标

- 在 ESP32-C3 平台上实现双路 RS485 接入的 DTU 设备
- 支持 TCP、UDP、MQTT、HTTP 四种透明传输模式
- 支持 Web 和 BLE 两种本地配置/维护入口
- 支持 PT1000 温度采集和现场校准
- 支持 OTA 在线升级和基本回滚保护
- 支持黑匣子事件记录与模块化日志开关

## 3. 总体架构

系统采用“主流程编排 + 组件化服务 + 队列解耦”的结构。

### 3.1 分层

1. 硬件与底层适配层  
   `wifi_mgr`、`rs485_uart`、`pt1000_adc`、ESP-IDF 驱动与系统组件
2. 基础服务层  
   `dtu_config`、`dtu_log`、`blackbox`、`ota_update`
3. 业务功能层  
   `net_transparent`、`cmd_handler`、`web_server`、`ble_service`
4. 应用编排层  
   `main`

### 3.2 核心模块

- `dtu_config`  
  全局配置中心，负责默认值、NVS 持久化、线程安全读写和配置变更事件广播
- `dtu_log`  
  按模块开关的日志系统，基于 `ESP_LOGx` 封装
- `blackbox`  
  独立分区上的环形关键事件记录
- `wifi_mgr`  
  根据配置启动 STA/AP/APSTA，并处理重连和失败回退
- `rs485_uart`  
  双路 RS485 半双工串口驱动，负责 DE/RE 控制和接收队列
- `net_transparent`  
  串口和 TCP/UDP/MQTT/HTTP 之间的桥接调度器
- `cmd_handler`  
  处理 `+++DTU_CMD:json+++` 格式的控制命令
- `pt1000_adc`  
  温度采集、阻值换算、校准偏移持久化
- `web_server`  
  提供内嵌配置页面与 REST API
- `ble_service`  
  提供轻量 BLE 配置、命令、日志读取入口
- `ota_update`  
  通过 URL 拉取固件并执行 OTA 升级

## 4. 启动与初始化流程

当前 `app_main()` 的初始化顺序如下：

1. 初始化 NVS
2. 初始化 `esp_netif` 与默认事件循环
3. 创建系统事件组 `g_dtu_event_group`
4. 初始化 `dtu_log`
5. 初始化 `dtu_config`
6. 初始化 `blackbox`
7. 初始化 `wifi_mgr`
8. 等待 WiFi 连接结果，超时后继续后续流程
9. 初始化 `rs485_uart`
10. 初始化 `pt1000_adc`
11. 初始化 `cmd_handler`，并注入温度和 OTA 回调
12. 初始化 `web_server`
13. 初始化 `ble_service`
14. 初始化 `net_transparent`
15. 初始化 `ota_update`
16. 打印启动摘要并结束主任务

这样安排的目的：

- 配置、日志、黑匣子尽早可用
- WiFi 基础连接先建立，再拉起 Web/BLE/透传等维护能力
- 命令处理器通过回调解耦 PT1000 和 OTA 业务实现

## 5. 并发模型

工程主要依赖 FreeRTOS 的任务、队列、事件组、互斥锁。

### 5.1 主要任务

- `rs485_rx_0` / `rs485_rx_1`  
  双路 RS485 接收任务
- `net_tx`  
  将串口上行数据发往当前网络协议
- `uart_a_tx` / `uart_b_tx`  
  将网络下行数据回灌到 RS485
- `net_reconn`  
  后台巡检并重建掉线的 TCP/MQTT 通道
- `cmd_proc`  
  异步处理特殊命令
- `ota_task`  
  异步执行 OTA 下载与升级

### 5.2 解耦方式

- `rs485_uart` 通过每路 RX 队列把串口接收和上层业务分离
- `net_transparent` 通过上行/下行队列把串口和网络通道分离
- `cmd_handler` 通过专用队列处理命令，避免在回调上下文做重操作
- `dtu_config` 和 `blackbox` 通过互斥锁保护共享状态

## 6. 核心数据流

### 6.1 普通透传数据

上行：

1. RS485 接收数据
2. `rs485_uart` 写入对应 RX 队列
3. 上层桥接后投递给 `net_transparent_send_to_network()`
4. `net_transparent` 根据当前通道模式发往 TCP/UDP/MQTT/HTTP

下行：

1. 网络协议回调收到数据
2. `net_transparent` 判断是否为命令帧
3. 若不是命令帧，则写入对应串口发送队列
4. `uart_a_tx` / `uart_b_tx` 调用 `rs485_uart_send()` 发回现场设备

### 6.2 控制命令数据

命令格式：

```text
+++DTU_CMD:{"cmd":"xxx"}+++
```

当前支持的主要命令：

- `read_temp`
- `calibrate`
- `status`
- `blackbox`
- `log_ctrl`
- `ota`
- `restart`

处理流程：

1. 任意入口收到命令帧
2. `cmd_handler_is_command()` 判定成功
3. `cmd_handler_submit()` 异步提交
4. `cmd_proc` 解析 JSON 并分发到具体业务
5. 通过响应回调将结果返回对应链路

说明：

- 当前 `log_ctrl` 命令要求带 `module` 和 `enable` 字段
- 但实际实现中只按 `enable` 做全局开/关，不做单模块命令控制

### 6.3 配置修改

1. Web/BLE 写入配置
2. `dtu_config` 更新内存中的 `s_config`
3. 同步写入 NVS
4. 广播 `DTU_CONFIG_CHANGED`
5. 需要重启才能彻底生效的配置由外部调用 `config/apply` 或重启命令应用

## 7. 配置模型

当前统一配置对象为 `dtu_config_t`，主要包含：

- WiFi 参数：`wifi_ssid`、`wifi_pass`、`wifi_mode`
- Socket 参数：`srv1_ip`、`srv1_port`、`srv2_ip`、`srv2_port`
- 串口模式：`uart1_mode`、`uart2_mode`
- 串口参数：波特率、校验位、停止位
- MQTT 参数：broker、client_id、双通道 topic、TLS 开关
- HTTP 参数：`http_url1`、`http_url2`
- OTA 参数：`ota_url`
- 串口绑定：`uart_bind`
- 心跳与重连：`heartbeat_en`、`heartbeat_interval`、`reconnect_interval`

### 7.1 当前默认值

当前代码中的默认配置来自 `components/dtu_config/dtu_config.c`：

- `wifi_ssid = "xiaowu"`
- `wifi_pass = "Wsy17820416856"`
- `wifi_mode = STA`
- `srv1_ip = "192.168.1.100"`
- `srv1_port = 8080`
- `srv2_ip = "192.168.1.100"`
- `srv2_port = 8080`
- `uart1_mode = TCP`
- `uart2_mode = TCP`
- `uart1_baud = 9600`
- `uart2_baud = 9600`
- `mqtt_client_id = "esp32c3_dtu"`
- `mqtt_pub_topic1 = "dtu/ch1/up"`
- `mqtt_sub_topic1 = "dtu/ch1/down"`
- `mqtt_pub_topic2 = "dtu/ch2/up"`
- `mqtt_sub_topic2 = "dtu/ch2/down"`
- `heartbeat_en = 1`
- `heartbeat_interval = 30`
- `reconnect_interval = 10`

## 8. 存储设计

### 8.1 NVS

NVS 主要用于：

- 全局配置持久化，命名空间：`dtu_cfg`
- PT1000 校准偏移持久化，命名空间：`dtu_cal`
- 日志开关位图持久化，命名空间：`dtu_log`

### 8.2 黑匣子分区

使用独立 `blackbox` 分区保存关键事件。  
结构上采用“头部 + 环形记录区”。

特点：

- 不与普通配置混用
- 适合长期现场追溯
- 记录内容更偏事件，不替代普通调试日志

### 8.3 OTA 分区

当前分区表：

- `otadata`
- `ota_0`
- `ota_1`

采用标准双分区 A/B OTA 方案。  
升级时把新固件写入空闲分区，重启后切换启动分区。

## 9. OTA 设计

### 9.1 当前实现方式

当前 OTA 由 `ota_update.c` 实现，核心方式：

- 通过 `ota_update_start(url)` 传入固件 URL
- 独立 `ota_task` 调用 `esp_https_ota()`
- 下载成功后自动重启
- 新镜像启动后在 `ota_update_init()` 中执行镜像有效确认

### 9.2 触发入口

可通过以下方式触发 OTA：

- Web 接口：`POST /api/v1/ota`
- 特殊命令：`{"cmd":"ota","url":"..."}` 

### 9.3 当前边界

- 当前实现用的是 `esp_https_ota()`，但 `cert_pem = NULL`
- 也就是说代码层已经走官方 OTA 封装，但证书校验没有做完整安全收口
- 当前进度接口较简化，只在成功后置 `100`

## 10. 对外接口

### 10.1 Web REST API

当前主要接口：

- `GET /`
- `GET /api/v1/config`
- `PUT /api/v1/config`
- `POST /api/v1/config/apply`
- `GET /api/v1/status`
- `GET /api/v1/status/temperature`
- `POST /api/v1/calibrate`
- `GET /api/v1/blackbox`
- `DELETE /api/v1/blackbox`
- `GET /api/v1/log_config`
- `PUT /api/v1/log_config`
- `POST /api/v1/ota`

### 10.2 BLE

当前 BLE 是轻量实现，不是完整设备管理面。

已实现能力：

- 读取配置摘要
- 通过 `key=value` 写入单项配置
- 触发配置应用并重启
- 提交命令帧给 `cmd_handler`
- 读取最近黑匣子文本

当前限制：

- `ble_service_notify_status()` 仍是预留接口
- 没有做完整状态订阅推送

## 11. 当前实现边界与风险

### 11.1 文档与实现差异已修正的重点

本次更新已按代码修正文档中的以下历史不一致项：

- 默认 WiFi 参数不是 `DTU_AP`，而是 `xiaowu / Wsy17820416856`
- RS485-A RX/DE_RE 实际是 `GPIO5 / GPIO6`，不是旧文档中的 `GPIO18 / GPIO19`
- Web 配置以双通道字段为主，如 `srv1_ip/srv2_ip`、`http_url1/http_url2`
- `cmd_handler` 当前并未实现按模块精细日志控制
- BLE 当前仍是轻量化入口

### 11.2 仍需关注的问题

- 固件体积接近 OTA 分区上限时，需要持续关注空间余量
- OTA 当前未做完整证书校验
- BLE GATT 能力还比较简化
- 文档中若后续新增命令、字段或接口，需要同步维护
